# Sol 6.1 候选方案：主力做完，难题再请专家

日期：2026-09-30。状态：开发候选，不是发布公告。稳定版仍是 v1.1.0。
同日后续安装校验修复、README 更新及新增行为实跑，见[发布准备记录](../release/sol61-readiness.md)；下文保留初期设计和验证经过。
初版设计时本地尚不能调用 Sol 6.1。当日后续已显式调用 `gpt-6.1-sol / high`，
完成一次临时项目的实现、自检与独立复核；原主控已对该 fixture 的六条要求给出 PASS。
详见[真实联跑记录](../../tests/artifacts/sol61-live-smoke.md)。当前仍不安装到全局、
不合并 main、不发布版本；原有静态检查和模拟推演不改称真实模型测试。

This is a development candidate, not a release. Explicit GPT-6.1 Sol/high calls
now work in a bounded Compatibility smoke. The original controller accepted all
six fixture requirements after checking actual files, diff, checkers and evidence.
This does not establish every runtime path, fresh-session custom-role discovery,
latency, or savings. The installed stable version stays unchanged.

## 为什么这样改

不再要求所有复杂工作都走“主控规划 → worker 执行 → 主控审核 → Host 再审核”。
大部分任务先交给一个足够强的模型做完。只有真正独立的工作才并行；
真正需要不同判断的问题才请专家。少交接、少重复读取、少重复检查，比多加一个角色更重要。

社区 [Issue #6](https://github.com/yehyakin/codex-prove/issues/6) 的反馈提示了
编排开销问题，但其中的估算不是配对 A/B 实验。本候选针对其描述的重复流程，
不据此声称性能已经提升。

## 已核对的官方信息

- [GPT-6.1 Sol 模型页](https://developers.openai.com/api/docs/models/gpt-6.1-sol)：
  精确 ID 为 `gpt-6.1-sol`。Standard 短上下文每百万 token 输入 $2、缓存输入
  $0.10、输出 $10。工具调用需要 Responses API；仅能列出模型或做文本问答还不够。
- [模型选择](https://learn.chatgpt.com/docs/models)：官方将 Sol 6.1 用于大部分高要求
  编程和 Agent 工作，Astra 留给最难的问题。这是选型依据，不是 PROVE 的实测结论。
- [迁移指南](https://developers.openai.com/api/docs/guides/latest-model)：先保留受支持的
  reasoning effort，减少同时改模型、推理预算和流程带来的混杂。
  Sol 6.1 不支持 `none` / `minimal`；本候选的两个 Sol 子代理均先保持 `high`。
- [Codex 子代理配置](https://learn.chatgpt.com/docs/agent-configuration/subagents)：
  子代理可能继承父配置，自定义角色配置优先。因此保留显式模型/effort、全新上下文和
  Host 调用记录检查；不让子代理自证不可见的元数据。

单价便宜不等于一项任务更便宜。输出和返工、缓存命中、调用次数、等待时间都要实测。
也不把 README 的 v1.1.0 预算例子迁移成新版“节省率”。

## 默认编排

| 情况 | 做法 | 不做什么 |
| --- | --- | --- |
| 清楚的小改动、已有命令即可完成 | 当前 Codex 直接做 | 不先检查所有模型是否可用 |
| 一条完整工作流，当前 Host 已是 Sol 6.1 | 在当前上下文完成 | 不因为跨文件就开新 Agent |
| 一条完整工作流，Host 是其他模型且交接值得 | 一个 Sol 执行者从理解做到自检，Host 验收 | 不额外配只做规划的 Sol |
| 只讨论方案 | 当前 Sol Host 或一个只读 Sol | 不开始实现 |
| 多条真正独立的工作流 | Sol 统筹，最少必要的 Sol / Luna 并行 | 不为每个文件或依赖阶段开 Agent |
| 难以裁决的问题、冲突结果、高后果独立复核 | 一次有边界的 Astra 只读咨询 | 不把整条流水线搬给 Astra |
| 规则明确的大量重复工作 | 可直接交给一个 Luna，给定客观检查 | 不额外配 Sol 规划，不让 Luna 猜业务语义 |

数据库 → API → 页面不自动等于三个 Agent。如果必须串行且一个 Sol 能保持上下文，
就让一个 Owner 做到底。确有独立分支时再分 Wave。同一文件、生成产物、共享配置
仍只有一个正在写入的 Owner，Host 自己写入也受这条约束。

### 四个稳定角色 ID，三个模型，不是固定四人团队

| Profile | 模型 | Effort | 子代理权限 | 用途 |
| --- | --- | --- | --- | --- |
| `prove-controller` | `gpt-6.1-sol` | `high` | read-only | 有价值的多任务协调，或纯分析 |
| `prove-complex-worker` | `gpt-6.1-sol` | `high` | workspace-write | 完整 Solo 任务或独立模块 |
| `prove-specialist-worker` | `gpt-6-astra` | `high` | read-only | 专项咨询、独立风险复核 |
| `prove-efficient-worker` | `gpt-6-luna` | `max` | workspace-write | 可客观验证的批量执行 |

这是明确的版本迁移：原 Astra 主控改为 Sol 6.1；原 Terra 常规执行改为 Sol 6.1；
原 Sol 专项改为只读 Astra。角色 ID 不变，方便原子安装、备份与恢复，
但不能把旧会话的角色映射当成新版已生效。Astra 的写权限是收窄，不是额外授权。

Terra 暂不进入默认分工。保留四模型只为“各有一个位置”会引入额外交接和维护。
这不等于宣称 Terra 在所有任务上更差；以后若有独立的成本/质量优势，再用数据决定。

同模型 Host 可以直接充当主控。保留用户当前受支持的 effort，不强迫改为 `high`，
也不伪称它执行了不同 effort 的配置。子代理则按配置精确调用；用户点名模型/effort
时始终遵守。能力不足只影响需要它的路径，不一律阻塞整个任务。

## 保留、调整和拒绝

| 决定 | 理由 |
| --- | --- |
| 保留显式启用、Host 权限边界、唯一写入 Owner、有限纠错 | 减少流程不能靠跳过安全边界 |
| 保留 Ponytail 已适配的复用与最小实现原则 | 不再增加 Hook、审查 Agent 或代码框架 |
| 默认 Solo，而不是默认“规划者 + 执行者” | 减少完整上下文重复传递 |
| 同任务沿用 worker，纠错只发变化和失败检查 | 不每次修复都重新规划整个任务 |
| 一次有效终验，变更后只重跑受影响检查 | 不重复消费同一份检查结果；跨模块集成仍需检查 |
| Astra 按问题进入，默认只读 | 避免它成为昂贵的必经终审 |
| 真正独立审核必须是新上下文 | 参与选方案的顾问不能再冒充该方案的独立审查者 |
| 普通审核反馈后的修正交给原 reviewer 复核 | 指出缺陷不等于接管设计；不每改一次就重开审核 Agent |
| 暂不降 Sol 到 medium、不改 Luna Max | 第一轮先测试流程；可用后再单独比较 effort |
| 不引入百分比路由配额、评分器或复杂账本 | 任务边界和实际收益决定分工，不追求固定模型占比 |

本轮独立编写编排说明与测试，没有复制新增第三方实现。
既有参考项目与许可证见[上轮调研](2026-09-25-peer-orchestration.md)及
[NOTICE](../../NOTICE)；Ponytail 的 MIT 署名原样保留。

### 初期列出的发布前检查（进度见发布准备记录）

1. 显式选择 `gpt-6.1-sol` / `high` 的真实工具读写已验证；继续验证新会话的自定义角色
   发现及实际映射。本轮会话仍暴露旧映射，因此用显式 profile 启动，没有改全局配置。
2. 在一次性测试项目中跑 Direct、Solo、Sol 并行、Luna 批处理、Astra 只读复核、
   依赖顺序、遗漏需求、写入冲突和超时恢复。本轮只覆盖预设 Compatibility 的一条
   Host + Sol 工作流、串行依赖、需求复核和缺失证据补全；不能外推到全部路由。
   Native Nested 仍单独标记，未通过就不宣传。
3. 验证旧版升级、恢复和新会话发现。经用户确认后才安装候选，保持全局配置及其他 Agent。
4. 对同一批任务比较“纯 Sol 6.1”和“候选 PROVE”：相同初始文件、要求、工具、预算和
   外部验收，至少三次交错顺序重复，计入所有规划/执行/审核/纠错 token、缓存、费用、
   总时长与缺陷。用旧稳定版作为额外对照，但不能把换主模型的收益全归功于编排。
   报告不占优的任务；没有完整价格/usage 时写未知，不写 0。
5. 只有实际数据支持时，再单独调整 Sol medium/high 或 Luna effort；不同时混改。
6. 更新中英文 README、配图、成本示例与发布记录，移除候选提示；最后才合并、推送、打标。

不承诺“到时改一个模型名就一定能发”。代码侧可先准备好，最终门槛仍是实际可用、
流程走通和质量达标；节省率另需完整对照数据。
