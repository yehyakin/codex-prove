# Sol 6.1 候选协议：边界情景模拟

这是**当前评估者的模拟推演，不是 GPT-6.1 运行时验证**。仅依据本次读取的 `SKILL.md`、`references/orchestration.md`、`references/runtime-notes.md`、四份 `.codex/agents/*.toml`，以及 `tests/fixtures/sol61-followup-inputs.json` 中的请求与能力描述。未读取其他评估、测试、研究、文档或 Git 历史。

下文描述拟采取的动作；没有执行情景中的修改、测试、取消操作或模型调用，没有启动子 agent，也没有修改全局设置。不对本次推演自评分，不据此宣称任务成功、模型能力或性能提升。

## 1. standalone-batch

- **路由：Solo，采用机械批处理例外。** 大量重复修改且具有精确映射与客观检查，值得整体委派；不是现成单命令的 Direct，也不因文件多或有两个空位就拆成 Coordinated。
- **子角色：1 个 `prove-efficient-worker`，`gpt-6-luna` / `max`。** 占用一个空位；不增设 Sol 规划者、独立 controller 或 Astra 审查者。Astra/high Host 保持当前设置。
- **写入所有权：Luna 独占这一批目录字段转换及检查确需产生的输出。** 执行前从任务上下文确定准确路径；输入未提供路径，不能凭空列文件。Host 不重复实现，不改 worker 正在持有的范围；无关文件、用户原有修改和外部副作用排除在外。
- **验收所有权：Host。** Luna 的自检和结果不是整体批准。

拟定后续动作与检查：

1. 记录当前目录、既有修改与未跟踪文件的基线，明确映射、范围、完整 checker、通过条件及可能写出的检查产物；复用适合的现有工具，不另建框架。
2. 以 `fork_turns="none"` 和完整的任务局部 packet 发起一次委派。核对权威角色映射及真实启动记录中的 Luna/max；不要求身份自述或空转握手。若 custom mapping 不符但支持精确显式选择，则使用相同指令的 explicit-profile 启动并如实记录；不能静默换模型或假定具有 TOML 声明的隔离。
3. Luna 按映射完成批次，运行用户要求的**完整 checker**，返回完整输出、退出状态、真实变更路径和候选快照/差异。若规则之外需要设计判断，交回 Host 处理，不自行猜测或扩权。
4. Host 检查实际文件及 diff，确认精确映射全部覆盖、无越界修改、checker 确实检查该候选且没有跳过内容或意外修改。后续修正交同一 owner，并只更新受影响证据；不能用抽样或成功摘要替代完整 checker。

## 2. tiny-independent-review

- **路由：Solo，附安全风险控制。** 实现虽只有两行，但用户明确要求独立安全审查；因此不符合零 agent 的 Direct。请求包含实现，不是整体 Assist；实现与后续审查的依赖也不需要额外 controller。
- **子角色：1 个全新 `prove-specialist-worker`，`gpt-6-astra` / `high`，只读。** Sol 6.1/high Host 复用当前上下文完成实现与本地测试；不另派执行 worker。审查者未参与选择修复，使用 fresh context 才能满足独立性。
- **写入所有权：Host。** 限定到本地 tenant filter、必要的现有测试及其授权产物；Astra 的 write scope 为 `[]`，不得实现建议。禁止部署。
- **验收所有权：Host。** Astra 提交限定范围的发现和证据，不成为第二 controller，也不批准整项任务。Host 的自检不能冒充独立审查。

拟定后续动作与检查：

1. 先做限定范围的只读检查：确认租户身份来自何处、过滤边界与相关调用方；记录原有修改和可恢复检查点。两行规模不降低安全后果，也不扩大操作权限。
2. Host 修改根因并补上当前缺失的跨租户回归检查，至少区分跨租户数据不可见与合法同租户访问仍有效；结合真实接口覆盖相关边界，避免添加无关框架。仅已有测试成功不足以证明租户隔离。
3. 候选形成后，核对可用容量以及 Astra/high 的权威选择记录，将原始要求、实际相关文件/diff、候选身份和测试证据交给只读新上下文。重点审查是否仍能绕过租户边界以及检查是否有区分力；不要求审查者先设计修复再“独立”验收。
4. 审查者仅运行范围内可用的非变更检查；需要写入或不适合只读执行的测试交回 Host。发现缺陷由 Host 修正，刷新受影响的测试和最终候选审查证据。若审查上下文后来参与选择修复，则不能再把它称为该修复的独立审查者。
5. Host 将原始要求、最终文件/diff、真实退出状态、跨租户覆盖与独立发现合并评审；候选变化使受影响旧证据失效。没有独立审查证据时不能声称已满足用户要求；仍不部署。

## 3. budget-cancellation

- **路由：Direct 停止与清点，不启动新的实现/恢复路线。** 用户要求停止，预算也已耗尽；两次无进展进一步终止原恢复路径。不能以新假设、换模型或恢复 packet 重置预算继续业务工作。
- **子角色：0 个新子 agent；不选择新模型或 effort。** 输入只说明有一个旧 worker 和它启动的命令可能仍在写入，没有提供其模型/effort，不能补造这些信息。保留旧任务标识和已有 ownership 记录。
- **写入所有权：受影响 fixture 暂时继续 held。** 未证实旧 worker 及其变更进程全部停止前，不转交、不重写、不清理；不会启动替代 writer。取消是授权的生命周期清理，不是新的实现尝试。
- **验收/报告所有权：Host。** 负责确认停止状态，并将有证据的已完成部分与未完成/不确定部分分开报告。

拟定后续动作与检查：

1. 立即停止分派、修复和新验证尝试；利用已知准确 task IDs，调用已授权的任务专属取消能力，分别覆盖旧 worker 和仍可能写入的命令及其任务关联变更进程。不能按宽泛进程名终止其他任务或机器上的无关进程。
2. 查询其生命周期状态，确认 worker 与变更命令都已结束。一次取消请求、超时、worker 的单独停止状态，或两个相同的文件快照都不足以证明所有 writer 已静止。
3. 若不能确认终止，保持 fixture 范围 held，报告尚未确认停止的具体 task/command；不靠接管、重试修改或全局清理“解决”。预算限制不阻止上述已授权、定向的取消与状态确认。
4. 确认静止后，保存并只读检查真实候选及 diff，保留用户修改；基于已有且仍适用的候选绑定证据清点完成部分。模拟输入未给任何实际完成证据，因此这里不能列出已完成的业务成果，也不能把旧 worker 摘要当成验收。
5. 报告用户停止/预算耗尽、两次无进展的历史、取消结果、未完部分和残留风险；有恢复需要时保留短 packet，但不自动重启或要求用户为本已授权的取消再次批准。

## 指令一致性与证据边界

- 在已读材料内，没有发现阻止上述三项选择的未解决实质冲突。四份 TOML 与候选文档的模型/effort 分工一致；这只是配置内容一致，不证明真实运行时采用了它们。
- “小修改保持 Direct”是通则；“小修改需要 child reviewer 时用 Solo”是明确例外。因此第二项不能借实现规模绕过独立安全审查。
- “预算耗尽停止尝试”与“仍可取消本任务在运行的 worker/command”分别约束业务推进与生命周期收尾，不冲突；停止请求不授权再开恢复路径。
- “高风险先只读分析”不等于整个已授权的本地修复只能分析；之后仍由唯一 writer 修改，并遵守禁止部署及独立审查要求。
- 输入中的“精确模型可用”仅是模拟前提；真实执行仍需核对权威映射、启动记录、容量和必要的权限边界。此次未获得、也未声称任何真实模型执行、测试通过或取消成功的证据。

## 4. review-correction：协议调整后的同上下文补充

本节由**同一评估者在原上下文中**重读调整后的 `SKILL.md`、`orchestration.md`、`runtime-notes.md` 与 `prove-specialist-worker.toml` 后追加。不是 fresh-context 评估，也不是任何真实模型运行；保留前面三个场景原文，仅评估新增输入。

- **决策与路由：沿用原运行，当前进行 Assist 型只读复核和最终验收。** 不因出现一次修正重建团队。输入没有说明原运行是 Solo 还是 Coordinated，不补造该拓扑。
- **新增 child 数：0。** 复用已有 `prove-specialist-worker`，`gpt-6-astra` / `high`，只读 `write_scope: []`；不换模型/effort，不启动第二 reviewer 或 controller，也不另做启动握手。
- **独立性：现有 Astra 可继续承担独立审查。** 它最初在 fresh read-only context 中开始，只指出缺少 tenant-denial 测试，没有选择实现或架构；修正由原 Sol writer 独立完成。普通缺陷反馈和复核修改不等于参与实质设计，新 diff 本身也不会使 reviewer 失去独立性。只有 reviewer 接管实质设计或实现时，才需要全新替代审查者。
- **所有权：原 Sol writer 保留原授权写域，目前无活跃 writer；此次复核不写。** 若发现仍需修正，交回同一 writer，不启动竞争写者。writer 的具体版本/effort 未在该输入中给出，沿用已有权威记录而不猜测或重置。最终验收沿用原 owner：Solo 为 Host，Coordinated 为原唯一 controller；Host 保留权限、集成和最终交付。Astra 只提供审查证据。

拟定后续动作与具体检查：

1. 给现有 reviewer 一份简短 follow-up：原要求、原缺陷、修正 delta、最终候选身份、真实相关文件/diff，以及绑定该新 diff 的测试输出和退出状态。不重传全历史，不重新要求用户批准正常复核。
2. reviewer 检查新增 tenant-denial 用例确实触及租户隔离边界，断言跨租户访问被拒或数据不可见；检查合法同租户行为仍被原要求覆盖。排除跳过用例、恒真断言、错误测试目标和仅名称匹配等假证据，并确认原缺陷已被有区分力的检查覆盖。
3. 核对所读文件/diff 就是证据对应的最终候选，逐项检查原要求与实际变更，没有只验证“新增了测试文件”。输入中的 passing tests 是模拟给定事实，不替代真实执行时阅读完整证据与检查其有效性。
4. 复用对该未再改变候选仍有效的测试证据，不为例行签字重复整套测试。若有具体缺口，仅补缺失或受影响检查；需要写入的检查交原授权执行者，Astra 保持只读。继续修正时保存尝试历史，并让同一 reviewer 复核新的相关证据。
5. 原验收 owner 将实际候选、原需求覆盖、有效测试证据和这次独立复核结果做一次最终评审；仅在全部原要求获得支持后交付。不能把 writer 的 passing 摘要、reviewer 的局部意见或此模拟推演当作整项任务完成证明。

本项未见未解决指令冲突：初次独立审查需要 fresh context；后续普通反馈与修正复核可以留在同一 reviewer context。它细化了前文“参与选择修复”的界限，并不要求每次 diff 变化都更换 reviewer。本节没有执行上述检查，也没有对模拟或任务作通过/失败评分。
